Hedged LLM Requests

Send the same request twice in parallel, take whichever response returns first, cancel the other. It is tail-latency insurance — it barely touches the median request, and it buys the clipped tail with token spend.

Turn the knob up when
You are latency-bound
A live demo, an interactive session where a stalled tool call is expensive in attention (staring at a spinner), or a time-boxed pitch-facing moment. Turning it up spends roughly a doubled token bill on that one call and buys back the worst outliers: the source measured 9.8s → 3.5s at the p99 end of its own production traffic.
Turn the knob down when
The tail is not the constraint
This is a dial, so the other end is not a failure mode — it is the default you already run, per call, and it costs nothing to sit there. The note is blunt about the regime, though: hedging is indefensible under cost-bound regimes where the tail isn't the constraint, and the median request, which was already fast, gains almost nothing from turning it up.

This panel departs from the usual pair. A trade gets a regime where it is simply the wrong call; a dial does not have one, because the knob is per-task and its low setting is the baseline. So the second column names where you leave it down rather than pretending there is a regime in which having the knob is a mistake.

Why each delta reads the way it does

speed-delta
+2
Tail only

Hedging is a per-task knob, not a standing win: it clips p99-style tail latency sharply — the source's own 9.8s → 3.5s, corroborated in shape though not in exact magnitude by independent hedging literature — while doing almost nothing for the median request, which was already fast.

It is scored +2 under the tail framing specifically, because that is the only regime where the technique does anything. That is exactly the "gives me a knob I didn't have" case the evaluation rubric flags as worth more than either endpoint. The mechanism is tail-latency insurance, not average-case speedup: it clips the requests that hit a slow model instance, a congested endpoint, or a transient stall.

The source reports the win came at standard-tier pricing — beating what a paid low-latency/priority tier would have cost.

cost-delta
−1
Evidence-backed, conditional

Hedging roughly doubles token spend per hedged call unless the losing request is caught and cancelled before it finishes generating. The source does not fully specify cancellation timing, so the true cost hit could range from near-zero (fast cancellation) to a full doubling (slow cancellation — e.g. a streaming response that is mostly done before the winner returns).

Scored −1 rather than −2 because cancellation-before-completion is the documented, achievable case, not the worst case. Cancellation timing is what determines how much of that doubled cost is actually avoidable.

quality-delta
0
Nothing about the output changes

The technique does not change what the model produces — same prompt, same model, take whichever response arrives. The two duplicate calls are typically identical, not diverse attempts, which is what separates this from Multi-Agent Debate and Low-Cost Model Swarms: those are Independence-mechanism techniques at the Model/Loop levers aimed at raising accuracy, while hedging is Independence at the Inference-config lever aimed purely at wall-clock.

attention-delta
0
Invisible once wired

Once wired up it is invisible to the user — no ongoing attention cost, unlike a technique that surfaces more decisions per turn. The setup itself is scored separately and low: effort: low.

dial
true
The knob is per-call

Hedging is fired unconditionally and proactively on the calls you choose to hedge, which is what makes it a knob rather than a mode: you decide, per slow call, whether to spend a second request. That distinguishes it from Model Routing (which model to use) and from retry-on-failure patterns, which react to an error rather than racing two attempts from the start.

Claude Code has no built-in option to hedge its own model calls — the underlying request to Anthropic's API is made by the harness and is not user-configurable at that layer. This is a pattern to implement around a specific slow tool call, not a harness setting to flip: a custom MCP tool or hook script wrapping a known-slow external API in the standard pattern (fire the primary, fire an identical second, take the first to resolve via asyncio.wait(..., return_when=asyncio.FIRST_COMPLETED), cancel the loser).

Workflow-level fan-out — firing two identical agent() calls and taking the first — is a much blunter, more expensive instrument: it duplicates a full agent turn rather than one HTTP request, so it only makes sense when a specific agent call is measured as having a heavy latency tail, not as a default. LangGraph has no built-in hedging primitive but supports the pattern directly inside a custom async node; the OpenAI Agents SDK shows no evidence of a built-in request-hedging feature, only parallel agent fan-out and error-triggered backoff. Microsoft Agent Framework and Kiro are not verified — no direct evidence was found either way, and that is recorded as unverified rather than assumed absent.

The Tail at Scale
"The Tail at Scale"; independent adaptive-hedging reports

Cross-checking the source's specific 9.8s→3.5s p99 figure against the broader hedged-request literature — the original distributed-systems argument for hedging, plus at least one independently-reported adaptive-hedging win of a similarly-shaped magnitude (P99 64ms→17ms on a non-LLM workload) — shows the mechanism and shape of the win (hedging clips tail latency specifically, barely touches the median) replicates across independent sources, even though the exact number stays single-source: not independently reproduced for an LLM workload specifically.

Both a trade and a dial
The scoring records this as both, and that is the rubric working rather than a contradiction. Trade and no-regret are read off the delta vector and are mutually exclusive with each other; dial is a separate marker that sits on top of either. Hedging is a trade by its vector — it spends cost to buy tail latency — and a dial because it is a per-task switch rather than a standing policy. Two further things the note flags about itself — the deltas were scored by an unattended triage-and-dive pass on 2026-08-24 and rest on published evidence and judgment, not on outcomes the user has observed directly; and the user's current regime is attention-bound and quality-bound, not latency-bound, so this is not where the technique earns its keep today. Worth prototyping only if a specific tool call in the workflow is measured as having a heavy tail, not as a blanket policy.
