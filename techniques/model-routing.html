Model Routing

Sending each request — and, in the interesting version, each turn — to the model that actually fits it. The point is not that it is cheaper. The point is that it converts a fixed cost into one you can turn up or down per task.

What the knob buys
It turns both ways
This is a dial, so there is no regime in which it is the wrong call and no second panel naming one — what changes with the regime is which way you turn it. Cost-bound or latency-bound: push mechanical turns down the stack — search, summarization, classification, subagent legwork onto a cheap model, effort: low alongside it. Quality-bound: leave the frontier model on everything and turn the dial the other way, spending more compute per decision where it counts. The same underlying mechanism — subagent model: fields, effort: fields — serves both regimes without new infrastructure, which is exactly why it is worth more than either endpoint on its own.
What the knob costs
attention-delta: −1
A knob is only free if nobody has to hold it. Manual routing — subagent frontmatter, effort flags, opusplan, fallback chains — requires you to decide the assignment up front and periodically re-verify it as tasks change. That is attention a single-model baseline never asks for, and it is charged in every position of the dial, not only the cheap end. This is the one users of this pattern tend to undercount.

Why each delta reads the way it does

dial
true
The class marker that decides everything

This is a dial, not a straightforward no-regret or trade. It does not fit no-regret — attention-delta is negative. It does not fit a single trade either: the delta vector is not spending one axis to buy one other, since cost, speed and attention all move, in different directions, depending on how it is configured.

What model routing actually hands you is a per-task knob: run cheap and fast when cost-bound, run frontier-everywhere when quality-bound, with the same mechanism serving both. The program's own evaluation rubric already names this technique as the canonical dial — routing is not primarily a saving, it converts a fixed cost into a tunable one.

cost-delta
+1
Not +2, deliberately

Routing mechanical, high-volume turns — search, summarization, classification, subagent legwork — to a cheaper model measurably cuts spend. RouteLLM's own benchmarks show large reductions, up to roughly 85% on their specific eval; Claude Code's per-subagent model override is free to configure.

It stops at +1 for two reasons. A misroute — a subagent needing more capability than its pinned cheap model has — creates retries that partially claw the savings back. And Fast mode, which often gets bundled into the same conversation as “routing,” is a 2x-price lever that actively costs more, not less.

quality-delta
0
Contingent, not guaranteed

Done well, routing should not touch output quality: the frontier model still handles the reasoning-heavy turns, and the cheap model only absorbs work a frontier model was already overkill for. Done badly — misrouting genuinely hard subtasks to a weak model — quality drops. The net expected effect against the stated baseline is neutral, contingent on router and config quality. Router quality is the crux, which is the same reason a misroute shows up on the cost axis as well.

speed-delta
+1
Turn-scoped, not session-scoped

Cheaper models are typically also faster per token, so routing mechanical turns to them shortens wall-clock for those turns. It is not +2 because the win is turn-scoped: a session dominated by the hard, frontier-routed turns will not see much aggregate speedup. Router overhead is a real cost rather than a rounding error here — classifier-based routers add a scoring pass, and industry commentary flags that it needs to stay well under about 100ms or the latency savings from picking a faster model get eaten by the routing decision itself.

attention-delta
−1
The tax nobody quotes

Manual routing requires the human to decide the assignment up front and periodically verify it is still right as tasks change — attention spent that a single-model baseline does not demand.

A learned router — RouteLLM-style, or Kiro's Auto — would push this back toward neutral by taking the assignment decision off the human. But none of the frameworks surveyed here ship a learned router inside Claude Code itself; all of the available knobs are manual or rule-based, set in advance by a person or a subagent definition. So the attention cost of the first concrete step — per-subagent overrides — is real, and it is not eliminated by the more automated alternatives shipping elsewhere in the ecosystem.

Fable & The End of the Free Lunch
Fable & The End of the Free Lunch

Argues Fable's step-up in capability came at a cost high enough that, unlike previous model generations, it is no longer a “free lunch” to wait for the next release to cover the gap — developers are now starting to think about which work goes to which model and how to give a weaker/cheaper model enough context to perform well, rather than defaulting everything to the frontier model. A direct restatement of this note's core premise (route by task, don't default to the most expensive model) from the angle of “the free ride from raw scaling just ended,” making the routing decision more consequential than it was a year ago.

Auto-research kernel optimization

A practitioner's writeup of an agent-driven GPU-kernel-optimization contest achieving a 232x speedup over baseline via continual profiling plus iterative refinement with Codex (placing 12th of 183). Evidence that the “spend more compute where it counts” half of the dial can pay off dramatically on the right task, though this is one contest result, not a controlled comparison against a fixed-effort baseline.

The Deadline Dividend
The Deadline Dividend

Argues that when inference gets faster, the saved time should not just be banked as lower latency — under a fixed deadline, it can instead be reinvested as more reasoning, verification or retry budget within the same time window. This reframes the effort/reasoning-budget discussion: instead of picking a fixed effort level per task type, a faster model lets more effort fit inside the same latency-bound window than before, without weakening the latency-bound regime commitment — a version of the dial that trades a model-speed gain for quality rather than for lower latency.

LiquidAI Prompt Router

A concrete, small-scale instance of the “cheap classifier decides” pattern — a 350M-parameter bidirectional encoder (LFM2.5-Encoder-350M-Prompt-Router) that scores a whole prompt against user-defined routing lanes in a single CPU-only pass, with the interactive demo explicitly framed around a “Device assistant” scenario. Models are getting dumber on purpose
Models are getting dumber on purpose

Argues recent model generations show a deliberate tradeoff — reasoning capability improving per-parameter while factual recall declines — because labs now expect models to lean on external retrieval and live data rather than memorized facts, cutting hallucination by letting models verify against a source instead of guessing. Bears on routing: a model chosen for recall-heavy tasks needs pairing with retrieval, while a reasoning-heavy task may not.

Why does Opus 5 feel worse?
Why does Opus 5 feel worse?

A practitioner reports Opus 5 feels worse to work with than its predecessors despite higher benchmark capability — it makes bold assumptions instead of asking for clarification, requiring more babysitting. Attributes this to benchmark optimization selecting for confident-guess behavior over appropriate uncertainty. A quality- and attention-cost data point that cuts against routing purely on capability or cost, since a “stronger” model can demand more human attention in ambiguous real-world tasks.

Netlify, via TLDR Dev
One prompt, 11 models, very different results
One prompt, 11 models, very different results

A test of 11 models generating the same static coffee-shop website (DeepSeek, Qwen, Kimi, GPT-5.6 Sol, Claude Opus 5, and others) found large variation in both output quality and credit cost — DeepSeek V4 Flash was cheapest at ~2.4 credits, GPT-5.6 Sol in low-effort mode averaged 141 credits, and higher-tier models like Opus 5 burned a lot of credits without results that clearly justified the cost. Concrete task-level evidence for the “route to the cheapest model that clears the bar” premise, and a reminder that “frontier” does not always mean “best value” even on the low-complexity end of the routing decision.

The model picker is a dead end
The model picker is a dead end

Argues the model picker itself is “a dead end” — a static, human-chosen model assumes one model handles all tasks optimally, which the author says is flawed. Lovable's alternative (“model independence”) aligns specific models to specific tasks and adapts as models improve, with a control plane that monitors builds and switches models to optimize performance — the vendor-side mirror of this note's own “routing has moved from a technique you build to a knob vendors ship” point, from a company whose product is the routing layer rather than the harness underneath it.

Nvidia's Switchyard router
Nvidia's Switchyard router reshuffles AI models mid-task

NeMo Switchyard is an open-source library that routes each step of an agent workflow to whichever model fits it best, paired with Nemotron 3.5 Lightning (a 30B open MoE model for high-volume agent tasks). Nvidia's own testing reports task costs cut “to a third” versus running Opus 4.8 alone while retaining frontier-level completion, and ~30% faster completion than Qwen3.6-35B at matching accuracy — another concrete per-step router, notable as a vendor shipping the model and the router as one open-source pair rather than a router in front of third-party models. Flagged in the source note as scoring evidence.

Cursor blog, via TLDR AI
How Cursor Router works
How Cursor Router works

Cursor Router's design is a concrete two-stage instance of the “cheap classifier decides, then routes” pattern — a complexity predictor (“Compass”) first decides if a turn needs a frontier model at all, then a learned taxonomy (task/domain/modifier, trained on hundreds of thousands of production turns using accept-vs-correct as the performance signal) picks which model historically performs best on that category. Reports concrete numbers: “above [frontier]-level user satisfaction at 68% lower cost” in Auto Intelligence mode, and Auto Balance “outperforms Opus 4.8 at 41% lower cost” while improving satisfaction — real evidence a learned router can beat manual tiering on both cost and quality simultaneously, not just cost.

A unified API for AI model routing

Google Cloud's API Gateway shipped model routing to public preview — a serverless ingress layer accepting OpenAI-compatible requests and dynamically routing them to Gemini, Claude, or OpenAI OSS-GPT, usable standalone or paired with the Gemini Enterprise Agent Platform. Where the confidence stops
Two limits on the evidence above, carried forward rather than smoothed out. RouteLLM's ~85% cost reduction at ~95% of GPT-4-level quality is specific to its MT-Bench/MMLU evals and its GPT-4-Turbo/Mixtral-8x7B pair — treat it as evidence a router can work, not a guarantee any given router hits those numbers on a coding workload. And the LangGraph and CrewAI per-node/per-agent model claims were cross-checked across secondary sources only, with no single authoritative doc page fetched for either, so those two specifically are researched-but-secondary rather than primary-source-verified.
