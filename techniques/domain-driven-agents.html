Domain-Driven Agents

A practice, argued by engineer Ernest Bednarczyk, for making legacy codebases legible to coding agents by applying domain-driven design — rather than by upgrading the model. His diagnosis: agents don't fail on legacy systems because the model is weak, they fail because the codebase itself never decided what its own concepts mean. An agent “invents a fourth spelling of a concept that already exists three times, because the codebase itself never decided which one was real.”

Reach for it when
You are quality-bound on a large, long-lived system
Favorable where domain-vocabulary drift is a real, live problem — a large, long-lived, multi-repo codebase where an agent keeps inventing a fourth spelling of a concept that already exists three times. It spends ongoing authoring effort to buy agent output quality on exactly that failure mode.
It is a poor fit when
You are attention-bound on a small codebase
A codebase too small for vocabulary drift to have occurred yet gets nothing from a manifest there is nothing yet to disambiguate — only the recurring authoring and drift-watching cost. That describes the user's own current vault-and-scripts ecosystem, per the note's own “How this could apply to me.”

Building and maintaining the manifest, glossary, and dual-declared context maps is real, ongoing authoring work layered on top of normal development — distinct from effort, which captures one-time setup. The dual-declaration mechanism specifically requires updating both sides of a relationship whenever either changes, which is a recurring tax, not a one-time cost.

Same reasoning as speed: keeping a manifest accurate as a codebase evolves requires a human to notice drift and update it — exactly the kind of task that gets skipped under time pressure. A stale manifest actively misleads an agent, arguably worse than having none, though neither source addresses staleness risk directly — this is this pass's own inference, and it is flagged as a judgment call rather than a sourced finding.

The practice, concretely

Four parts. Strategic/tactical split — humans decide what changes and own architectural judgment; agents own mechanical implementation and refactoring within a context whose vocabulary is already settled. Domain manifests — each repository carries a .workflow.json declaring its bounded contexts and glossary, the ubiquitous-language documentation DDD calls for, made machine-readable so an agent can load it as context rather than infer it from inconsistent code. Context maps — a generator walks a set of repositories and produces unified documentation of all contexts and the edges between them, with the relationship type declared explicitly (conformist, anticorruption layer, and the rest of standard DDD context-mapping vocabulary). Dual declaration — each inter-context relationship is declared from both sides, so a generator can automatically flag disagreement between what one repo claims about a dependency and what the other side actually exposes.

In Claude Code, the closest fit is a project's CLAUDE.md linking to — or a SessionStart hook injecting a summary of — a checked-in glossary file per bounded context, so the ubiquitous-language declaration is context supplied once per session rather than prose repeated in every prompt. The dual-declaration disagreement check is a better fit for a small script wired into a PreToolUse or CI check than an agent-authored document — a Constraint/Feedback pairing more than a Context-lever artifact. A skill scoped to “implement within bounded context X,” loading that context's glossary and explicitly refusing to introduce new domain terms, would operationalize the strategic/tactical split without inventing new tooling.

No framework surveyed — LangGraph, Microsoft Agent Framework among them — treats inconsistent domain vocabulary as a first-class problem the framework itself solves. In every case the manifest and glossary idea is something a team builds on top of whatever orchestration layer it already uses.
