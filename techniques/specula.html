Specula

A named tool, not a general pattern: an agentic system that auto-derives formal TLA+ specifications from code, model-checks them to find concurrency bugs, validates code-spec conformance via trace validation, and reproduces any bug it finds at the code layer as a precisely-timed integration test. A formal-verification approach to agent-driven bug finding.

Reach for it when
You are quality-bound, with genuine concurrency exposure
Async coordination, shared state, locking, distributed protocols. It spends real compute cost and real one-time setup effort to buy a bug class the user's current workflow has no other way to reach, at the price of frontier-model spend and a real toolchain to stand up.
It is not a fit when
You are cost-bound, or there is no concurrency
Not a fit at all under a pure cost-bound regime — weak models don't work — or for codebases without meaningful concurrency, where there is nothing to find.

Why each delta reads the way it does

quality-delta
+1
Not +2, deliberately

The reported results are strong on their own terms — 249 bugs across 48 real systems, 68 independently confirmed and 24 already fixed by upstream maintainers (external validation the paper doesn't control), and a measured 0-false-positive rate on the current version because every finding is reproduced as a runnable integration test rather than reported as an abstract counterexample.

Capped below +2 by two unresolved limits the paper itself surfaces or that the blog's close reading identifies: the tautology problem (spec quality is bounded by how well the self-improving loop escapes the very code it's checking — strong empirical results, unresolved in principle) and the composition gap (no reasoning across service boundaries, so the technique's real scope is single-service concurrency bugs, not distributed-system bugs generally despite the "distributed systems" framing).

cost-delta
−1
No cheap-model way in

This is real added spend against the baseline of zero — a $57-median-per-system figure (per the blog; not independently re-confirmed here) for 1.4–9.9 hours of agent compute, and critically, spend that only pays off at frontier-model tier: the SysMoBench and bug-count-by-model results both show the technique effectively stops working below Opus-class capability, so there's no cheap-model way to capture partial value the way, say, Model Routing's tiering pattern allows elsewhere.

speed-delta
0
Out-of-band, not blocking

Framed and run as an out-of-band batch/CI-style pass (specula run, hours of wall-clock) rather than a blocking step in the interactive coding loop the way a PreToolUse gate in Agentic Code Quality is — it doesn't slow down the turn-by-turn Claude Code session, so no delta against the baseline's interactive speed, even though it costs real wall-clock elsewhere.

attention-delta
+1
Removes an expertise requirement

The genuine unlock: formal verification of concurrency properties has historically required a human who can write TLA+ by hand, which the user does not have and would otherwise have to acquire or hire for. Push-button spec derivation removes that expertise requirement entirely for the cases it handles.

Not +2: the 249 findings still need human triage and real fixes — this automates the finding step, not the deciding what to do about it step, and the self-improving loop's own tautology risk means results still warrant a skeptical read rather than blind trust.

dial
false
A pass you run or don't

Not a dial: this is a whole-system verification pass the user runs or doesn't, not a per-task knob with a cheap-and-expensive setting the way effort levels or model routing are.

The load-bearing constraint

Model capability gates the whole technique — this is the single most load-bearing finding. The paper's own SysMoBench scores (syntax/runtime/conformance/invariants/overall) show Opus-4.8 at 100% across the board, Sonnet-4.6 at 93% overall, and Haiku-4.5 collapsing to 47% overall (56% runtime, 51% conformance, 17% invariants) — and separately, Sonnet-4.6 found only 10 of 62 bugs Opus found on the same systems, Haiku found none. This isn't a technique that degrades gracefully with a cheaper model; below frontier tier it stops working.

Two further limits sit alongside it. The tautology problem: specs are derived from the code being checked, so a bug baked into the implementation can get baked into the spec too, silently escaping detection. The paper's own self-improving loop (trace validation pulling specs toward code behavior, model checking pushing back toward the invariants) is the stated mitigation, and the reported false-positive rate is genuinely strong evidence it works in practice — 0 false positives across 136 bugs in 14 systems for the current version, versus 5 (Agent-Raw baseline) and 2 (Agent-TLA+ baseline) on a 5-project comparison — but the paper doesn't fully resolve the circularity concern in principle, only shows it doesn't manifest much in these results. Only 21.1% of derived invariants are protocol-level (implementation-independent) per the blog's reading, which is the more precise version of the same worry.

And no composition across services: Specula builds a monolithic per-module model with mocked interactions rather than reasoning across a distributed system's service boundaries — a real scope limit for anything beyond a single-service concurrency bug.

Resource floor. Python 3.10+, Java 21+ with Maven, GitHub CLI, a TLA+ model-checker toolchain, and the README's own recommendation of 32GB RAM / 100GB disk — this is not a lightweight hook, it's closer to standing up a second local toolchain.
