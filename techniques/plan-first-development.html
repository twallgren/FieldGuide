Plan-First Development

Always producing — and reviewing — a plan before the agent writes any code. Harnesses increasingly bake this in, on the theory that steering is cheapest before implementation starts. The interesting question is the threshold, not whether to plan.

Compared to what
An agent session that goes straight from prompt to implementation with no explicit plan step (Claude Code’s default/manual mode used conversationally, no /plan), on a moderately ambiguous multi-file task — the regime where the plan/no-plan choice is actually live. On trivially small mechanical edits the honest baseline comparison flips, which is exactly why this is scored as a dial rather than a flat trade.

What the knob buys
It turns both ways
This is a dial, so there is no regime in which it is the wrong call and no second panel naming one — what changes with the task is which way you turn it. Turn it on for multi-file changes, ambiguous requirements, and unfamiliar codebases, where steering before any code exists is cheaper and more effective than steering a diff. Turn it off for small mechanical edits, where it is pure overhead: practitioner writeups on spec-driven development converge on the line that process overhead can exceed the actual work on a minor refactor or UI tweak, and reviewers have complained that Kiro-style spec files are more to review than the code itself. The switch is per-task in Claude Code — Shift+Tab, /plan, or a project default — which is what makes the threshold a live question rather than a policy.
What the knob costs
Three axes, every time you turn it on
Unlike a dial that trades one axis for another depending on position, this one bills on three whenever it is on: extra tokens for the plan turn and the approve/refine cycles, added wall-clock before any code is written, and a human checkpoint that acceptEdits/auto-mode workflows do not require. The attention charge is the one to watch, because it is load-bearing rather than incidental — a bad plan approved without reading is worse than no plan at all.

Why each delta reads the way it does

dial
true
Not a flat trade

The technique is explicitly per-task-switchable in Claude Code (Shift+Tab, /plan, or a project default), and the entire question this note circles is finding the complexity threshold where the switch should flip — that is the definition of a dial in the program's rubric, not an unconditional trade.

Kiro's implementation leans toward a fixed policy — spec-first as the default posture, with Quick Spec as the escape hatch — which is a narrower dial than Claude Code's. Worth noting, since “Kiro made it mandatory” is closer to “defaulted the dial to on” than “removed the dial,” given Quick Spec exists.

quality-delta
+1
Real but bounded in scope

Plan mode's own selling point — and the reason harnesses converged on it (Kiro, Magentic, LangGraph's plan-and-execute) — is that steering before any code exists is cheaper and more effective than steering a diff. LangChain's own writeup on plan-and-execute claims better task-completion rate versus ReAct-style no-plan agents by forcing the planner to think through the full step sequence up front, and Magentic's task ledger exists to keep multi-step work coherent.

This isn't free, though. Nearform's critique is that plan mode alone doesn't cover product-level coherence, only feature-level — so +1 (better) rather than +2 (much better) reflects that the mechanism is real but bounded in scope.

speed-delta
−1
By construction

Writing and reviewing a plan before touching code is by construction added wall-clock versus jumping straight in. This is the same overhead multiple independent sources (Nearform, allegro.tech, xpromx.me) call out specifically for Kiro-style spec-driven flows on small tasks, where the process outlasts the change itself.

cost-delta
−1
Smaller hit than a swarm

Extra tokens for the plan-generation turn and the back-and-forth to approve and refine it (Ctrl+G edits, “no, keep planning” cycles) beyond what a single implementation turn would cost. It is a smaller hit than a multi-agent debate or swarm, since it is still a single agent and a single extra artifact, not multiple independent attempts.

attention-delta
−1
The mechanism is the cost

The plan is a document the user is meant to actually read and approve, not a fire-and-forget step — that is the entire mechanism (constraint plus feedback happening before code exists), but it means a human checkpoint that acceptEdits/auto-mode workflows don't require.

This is the axis most likely to flip sign in the attention-bound regime specifically because a bad plan approved without reading is worse than no plan at all — plan-as-theater. So the honest score treats the read-it-properly cost as real rather than assuming rubber-stamping.

the failure mode
drift
A loop problem, not a context one

Plan-as-theater: the agent writes a plan, then drifts from it during implementation with nothing enforcing consistency. This is a loop problem, not a context problem — nothing re-checks the plan against the diff once implementation starts, which is why the mechanism only holds if something closes the loop: a fresh-context reviewer diffing implementation against the approved plan, or a checklist re-read before declaring done. Plan mode itself does not do this. Plans are also a review surface in their own right — a fresh-context agent can critique a plan far more cheaply than it can review a diff.

adapt.com, via TLDR Dev
Build Wide, Ship Narrow
Build Wide, Ship Narrow

Argues the tight-planning-before-coding workflow has evolved under AI-assisted development toward broader initial builds explored before review, with a demo of working code preceding code review and the change then broken into smaller, independently reviewable PRs afterward. This inverts this note's core sequencing claim (plan and steer before implementation, because steering is cheapest early) for at least some task shapes — worth weighing against the note's own regime-fit reasoning rather than treated as a blanket rebuttal, since exploratory/uncertain-scope work may tolerate build-first better than well-specified work does.

Nearform
Why plan mode is not enough
Why plan mode is not enough: better outcomes with spec-driven development

Luca Lanziani (Nearform) argues plan mode works well for implementing a single feature but doesn't scale to planning a whole product — composing features into a coherent whole needs product-owner/business input that a single-agent plan mode doesn't solicit. Nearform's proposed fix is BMAD (Breakthrough Method of Agile AI-Driven Development), a multi-role agent framework (PM, architect, scrum-master, dev agents). This doesn't contradict plan-first as a technique so much as bound its scope: it's a claim about what unit of work plan-first is good at, not about whether planning-before-coding helps.

Where the confidence stops
The quality claim rests on LangChain's own writeup of its own pattern — a vendor reporting better task-completion rate for plan-and-execute versus ReAct-style no-plan agents — plus the fact that several harnesses independently converged on planning gates. That is convergence, not a controlled trial, and no trial count sits behind any delta here. The threshold this whole note turns on — where the complexity of a task crosses from “planning is overhead” to “planning pays” — is named as the interesting question and is not answered anywhere in the source material, by me or by anyone cited. Two of the four logged perspectives argue the sequencing should invert for at least some task shapes, and that challenge is unresolved rather than dismissed.
