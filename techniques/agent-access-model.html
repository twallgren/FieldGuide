Agent Access Model

Give an agent task-specific, short-lived credentials with enforcement at the harness and network layer, instead of letting it inherit whatever your own standing credentials can reach. Guardrails with real enforcement — not a policy document nobody checks.

Reach for it when
You are quality-bound, or exposed
Many agents, shared credentials, or a genuine risk of one compromised task cascading into standing access. That is the regime the trade is worth making under — it buys containment at the cost of speed and attention, and only an exposure-driven or quality-bound threat model justifies the bill.
The trade goes thin when
One harness, one machine, one human
AAM is designed for a multi-agent, multi-tenant enterprise problem. Under a single-machine, attention-bound regime the marginal benefit over Claude Code's existing static allowlist is thin relative to the setup cost — unless the threat model changes, e.g. running several concurrent agents against shared production credentials.

Why each delta reads the way it does

quality-delta
+1
Containment, in principle

Task-scoped, sender-constrained, expiring credentials give a genuinely narrower blast radius per task than a ceiling set once and left in place. If an agent is compromised or goes off-script mid-task, there is less standing access to abuse than under a static allowlist. This is a real containment improvement in principle.

It is researched, not measured: the reading rests on Cloudflare's own architecture writeup and on Microsoft's independent, shipping just-in-time-elevation guidance pointing the same direction — not on anything run locally.

cost-delta
0
Wrong axis entirely

This is not a token or spend lever at all — it is about credential exposure and access scope, not LLM call efficiency. No plausible cost impact in either direction.

speed-delta
−1
Small per task, but unavoidable

Real task-scoped credentials require an actual issuance step — token exchange, key binding — at the start of each task, overhead a static, already-resolved allowlist does not pay. Small per task, but real, and there is no way to get the containment benefit without paying it somewhere.

attention-delta
−1
The deciding axis

AAM is designed for a multi-agent, multi-tenant enterprise problem — many agents, many humans, shared infrastructure, credentials that need central revocation. A single harness, run locally under one person's standing trust, is not that problem.

Building or adopting the broker/proxy infrastructure AAM actually needs — a token-exchange service, sender-constrained key management — to realize its benefit costs real setup and maintenance attention that a single-user settings.json allowlist does not ask for. And the Grant Review Loop's own attention-saving pitch only pays off once that infrastructure exists to generate the activity logs it reviews.

dial
false
An architecture, not a knob

Recorded as false in the note's frontmatter. There is no per-task knob handed to the user here — the technique is an access architecture you either stand up or do not.

What effort: high actually consists of

One-time setup cost · amortizes, unlike the deltas

Cheap to run, expensive to adopt — a distinction the four deltas do not show. The note is specific about where the setup cost lands:

A token-issuance layer the harness does not have. Claude Code's permission system (settings.json allow/deny/ask, evaluated deny → ask → allow with rules merging across managed/CLI/local/project/user scopes) is the existing Constraint-at-Tools mechanism — but it is a static ceiling set once, not task-scoped or time-boxed. There is no built-in primitive for “this permission expires when this task ends” or “this token is bound to this specific run.” Expiring and sender-constrained credentials need an actual token-issuance layer.

A Grant Review Loop with no built-in analog. Proposing policy tightening from observed activity logs would need a custom script parsing session transcripts and hook events, diffing granted permissions against what was actually invoked, and surfacing over-permissioned rules to prune — essentially a permission-usage auditor for settings.json, which does not currently exist as a Claude Code feature or known community skill.

A gateway for the secrets-in-tool-calls half. For keeping raw API keys out of the agent's context — as opposed to filesystem/bash permission scoping — a OneCLI-style gateway in front of MCP server calls is the closer fit than anything in Claude Code's own permission model, which gates actions, not what credentials a tool call carries.

The cheap approximation, and its ceiling. Without building real broker infrastructure, the closest available move is swapping in a narrower settings.local.json per task type via a wrapper script or a SessionStart/PreToolUse hook that tightens the active rule set for the kind of task starting. That gets partway to “task-scoped” — but not to “expiring” or “sender-constrained.”

Where it already ships elsewhere

Microsoft Agent Framework / Microsoft Entra Agent ID — verified via Microsoft Learn and the Security Blog. Agent identities are distinct from human or managed identities, credentials are configured on an identity “blueprint” rather than per-instance, and Microsoft's own production guidance explicitly recommends just-in-time elevation — narrowly-scoped, time-bound grants for the duration of one workflow — over standing broad access. The closest verified real-world analog to AAM's task-scoped credential outside Cloudflare's own writeup, and it is shipping, not a proposal.

LangGraph Platform — verified via LangChain docs. @auth.authenticate and @auth.on handlers scope what a given run's credentials can touch, with resource-level filtering so a user only sees or modifies matching threads, assistants and runs. Closer to per-run scoping than Claude Code's static file-based allowlist — but a feature of the managed Platform deployment layer, not of running a LangGraph graph locally.

OpenAI Agents SDK — verified via SDK docs and the OpenAI developer community. Ships tool- and agent-level guardrails for input/output validation, but no built-in ephemeral-credential or task-scoping primitive. A thread on OpenAI's own developer forum names this explicitly as an open gap: agents pass through API keys with full access, no scoping, no revocation short of rotating keys for everyone — developers solve it with external tooling, not with the SDK.

AWS Architecture Blog, via TLDR Dev
Graduated autonomy
Closing the AI Agent Trust Gap with Graduated Autonomy

Proposes a dynamic, reputation-based permission model instead of a fixed scope — agents start read-only and earn expanded write/execute access through a weighted 0-100 score across five dimensions (accuracy, safety, consistency, compliance, efficiency) over a rolling 50-action window, promoting slowly through four tiers (T1 probation → T4 autonomous) but demoting instantly on a violation. A different axis from AAM's task-scoped-credential thesis and Vercel Connect's auto-expiring tokens: those narrow what an agent can reach per task, this narrows how much an agent can do based on its own track record. The two are composable rather than competing.

How we contain Claude

A Policy Algebra for Trust-Preserving Agentic AI Execution

Proposes enforcing an agent's permissions continuously throughout a task rather than only at the start — e.g. a refund agent staying capped at its spending limit and escalating to human approval mid-task, not just when the task is granted. Nuances
The Hacker News
GhostSplice
Malicious MCP servers can split a malicious instruction across fragments

The “GhostSplice” attack shows malicious MCP servers can split a malicious instruction across a tool description, a tool result, and a server message — each fragment individually benign, only dangerous combined — raising average model compliance from 42% to 82% across 11 models tested (some going 0%→100%). A distinct attack surface from AAM's credential-scoping claim: splitting does not require elevated access, just unchecked tool-output-to-tool-argument flow, so credential scoping alone would not stop it. The researchers' fix is treating server output as data, not instructions, and blocking values from flowing unchecked between tool calls.

An OSS credential gateway that injects API keys into agents without exposing raw keys, with pattern-based routing for multi-agent setups — a concrete, shipped mechanism for the task-scoped-credential half of AAM's design (agents never hold the standing credential itself, only a scoped injection). The distinguishing claim, sharpened rather than resolved
The claim this note flagged at promotion — task-specific, short-lived credentials versus a static ceiling — held up under research and got sharper rather than settled. OneCLI, the concrete shipped tool logged in the Perspectives log above, turned out to implement the weaker version. Verified directly against its own architecture docs: OneCLI does per-agent static credential mapping with pattern-based routing, not per-task expiring tokens. It solves “don't expose raw keys to the agent's context” — a real, adjacent problem — but not “narrow scope per task and expire it,” which is AAM's actual claim. The two are easy to conflate and worth keeping distinct on any future entry. The honest takeaway from the whole dive is pattern, not tool: the broker, token-exchange and sender-constrained machinery is enterprise/multi-tenant infrastructure a single-user setup likely should not build — but the shape of the idea, don't let permission scope only ever accumulate, narrow it per task where cheap to do so, is adoptable today without waiting for it.
