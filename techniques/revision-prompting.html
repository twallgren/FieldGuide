Revision Prompting

When the input to a generated artifact changes slightly, hand the model the original input, the original output, and a diff — and ask for a minimal patch instead of a fresh full regeneration.

Reach for it when
You are cost-bound or latency-bound
It spends attention to buy cost and speed, which is a reasonable trade under a cost-bound or latency-bound regime. The target case is any LLM-generated artifact — a summary, a plan doc, a generated spec, a config — that needs updating when its source material changes a little.
It fits poorly when
You are attention-bound or quality-bound
A poor fit for the user's stated attention-bound/quality-bound current regime, since it specifically demands more scrutiny exactly where the user wants to spend less. Not evaluable as no-regret given the quality-delta uncertainty, and not a dial since there is no per-task lever to turn.

Why each delta reads the way it does

cost-delta
+1
Direction, not magnitude

The vendor's own reported figure — ~65% cost reduction, from revisionprompting.info — is self-reported production data with no independent benchmark, no named company backing it beyond a personal contact address, and no measurement against coding-agent-generated artifacts specifically. The use cases cited (invoice extraction, documentation translation) are a different shape of task.

The direction is plausible on mechanism alone — patching a small diff is cheaper than reprocessing a full input — so this scores positive. But the magnitude is unverified enough that the score rests on judgment about the mechanism rather than on a trustworthy number.

quality-delta
0
Two forces, opposite directions

This is the genuinely uncertain axis. A bad revision patch can silently corrupt the output in a way that isn't obviously wrong on inspection — a different and arguably worse failure mode than a bad full regeneration, which tends to be visibly wrong against the known-good source and easier to catch.

The vendor's claim of "more consistent" outputs pulls the other way, but that claim is equally unverified. Scoring 0 rather than picking a side reflects that the accuracy question and the failure-cost question point in opposite directions and neither has independent evidence.

speed-delta
+1
The best-supported delta

Generating a bounded patch is architecturally less generation work than a full regeneration, which is the same direction as the vendor's ~80% time-reduction claim even though the magnitude is unconfirmed. This is the delta with the most mechanistic support: less output to produce should take less wall-clock, independent of whether the vendor's specific number holds.

attention-delta
−1
Where the uncertainty lands on you

This is where the quality-delta uncertainty actually lands on the user. Because a corrupted patch isn't obviously wrong on a casual read — the Verifiability / Failure-cost tension pair in the program's evaluation rubric — using this technique responsibly means scrutinizing patches more carefully than a full regeneration, not less. It spends less compute while demanding more of the human's attention, precisely to catch the failure mode the speed and cost gains introduce.

false
Architecture, not a knob

No per-task adjustable knob here — it is an architectural choice about how a generated artifact gets updated (patch vs. regenerate), applied uniformly to that artifact type, not something tuned per invocation.

What it is, and what it is not

It is not the same as how coding agents already edit files. Claude Code and similar agents already emit diffs and patches as their output format when touching source files. Revision Prompting is about the input to generation changing and the model producing a patch to a previous output accordingly. Concretely, it is closer to "the PRD I generated changed because one paragraph of the source ticket changed — patch the PRD instead of regenerating it" than to "edit this source file."

It is also distinct from prompt caching, which it sits adjacent to: caching avoids reprocessing unchanged context tokens, while Revision Prompting avoids reprocessing an unchanged output when only part of the input changed. The failure modes differ too — a bad cache hit returns stale-but-recognizable content, while a bad revision patch can silently corrupt the output in a way that isn't obviously wrong on inspection.

No built-in primitive does this in Claude Code. There is no persisted mapping from a source input to a previously generated output that a later run could diff against, so approximating the pattern requires custom scripting: store a fingerprint and copy of the generated artifact alongside its source, diff the source on a later invocation, construct a prompt containing the original source, original output, and source diff that explicitly asks for a patch, then apply the returned patch. No named framework was found to ship a native "patch-based regeneration on source diff" primitive either — stated plainly rather than guessed. LangGraph's checkpointing could hold a prior output for comparison, but the diffing and patch-only prompt construction would still be custom node logic; the OpenAI Agents SDK and Microsoft Agent Framework have no documented equivalent.

What this pass surfaced but did not settle
Whether the failure-mode risk — silent patch corruption vs. visibly-wrong full regeneration — is serious enough to disqualify this for anything beyond low-stakes internal artifacts is a judgment call the source dive flagged and left open. It would take an actual side-by-side trial against a real repeated-update artifact to know whether the corruption risk shows up in practice, and that experiment is currently on hold. Worth prototyping only once the hold lifts, and only against a real repeated-update artifact in the user's own workflow — the vendor's two headline numbers are unverified enough that they shouldn't be treated as evidence on their own merits.
