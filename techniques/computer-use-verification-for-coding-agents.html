Computer-Use Verification for Coding Agents

Coding agents using screen and computer-use tools to verify their own work — reproducing a reported bug by actually driving the UI, exercising an implementation against its spec, attaching screenshots or video to a PR as evidence. The framing that matters is a split: evidence-capture is solid and shipping widely; evidence-judgment — who decides pass/fail — is contested, and is where the risk lives.

This panel departs from the usual pair. A trade gets a regime where it is simply the wrong call; a dial does not, because the knob is per-task and its lowest setting is the baseline. So the second column names where you turn it down rather than inventing a regime in which having the knob is a mistake.

Why each delta reads the way it does

dial
true
Both a trade and a dial

This note records a trade in its evaluation and dial: true in its scoring, and both are correct. The rubric is explicit: no-regret and trade are read off the delta vector and are mutually exclusive with each other, while dial is a separate, non-derivable marker that sits on top of either. By vector this is a trade — it buys quality and attention with cost and speed. By marker it is a dial.

The knob is verification depth, and the note names four settings: skip it for a low-stakes internal tool, capture-only for a quick sanity check, capture plus a deterministic check for anything shipped, capture plus human review for anything high-stakes. That knob is distinct from the underlying capability — having browser and simulator tools available does not itself decide how deep to go on a given task.

The note also records that the class reads differently at different settings of that same knob: trade at the capture-only, self-graded end, where it buys some quality and attention at real cost with a live risk of false “done” claims; and closer to no-regret in the capture-plus-deterministic-check design, relative to no verification at all, since that design does not introduce the self-grading risk.

quality-delta
+1
Not +2, deliberately

Real UI evidence beats no verification at all and catches classes of bugs a code-only check cannot — visual regressions, actual click-through breakage.

It stops at +1 because the practitioner evidence is explicit that agent self-grading of screenshots is unreliable: the Reward Hacking Benchmark reports 0–13.9% exploit/“cheating” rates across frontier models, correlated with RL-heavy post-training, and Cognition's own docs admit agents sometimes force application state via JS instead of genuinely exercising the UI. The delta is real only when judgment is separated from capture — deterministic or human-graded. Collapsed into pure agent self-grading, this could easily be a wash or a regression on Failure cost: confident-looking but wrong “done” claims fail silently instead of loudly.

cost-delta
−1
Tool calls, not just tokens

Extra tool calls — navigate, interact, screenshot, and ideally a separate non-LLM check — cost more tokens and turns than skipping verification, or than a pure code-check gate like Merge Queue's checkCommand.

speed-delta
−1
The shape every gate has

Same shape as every other Environment/Tools-lever gate scored so far in this program — Merge Queue, Cloudflare Codex. An extra step before “done” is claimable.

attention-delta
+1
Conditional on the design choice

When the verification is trustworthy — meaning judgment is separated from capture — it genuinely substitutes for the user personally checking the UI. Real time back. This is conditional on that design choice, not automatic.

Who judges the evidence

The strongest practitioner evidence explicitly rejects agent self-grading of its own screenshots. Vadim's “Agent Explores, Code Judges” architecture strips the LLM out of the verdict step entirely — a Playwright navigator collects evidence, a pure-Python verifier makes the pass/fail call — specifically because “self-grading systems collapse audit trails when agents decide both what to check and whether checks passed.”

The note's concrete hardening path, in its stated order of strength: a ui-verify skill standardizing the loop — start dev server, navigate and interact via the browser or simulator tools, capture a screenshot, then run a separate, non-LLM check where one exists (console-error scan, network-status scan) before the model narrates success. Then a Stop hook that blocks marking a UI task complete unless a verification artifact exists for the session. Then PR and commit templates requiring a linked artifact path, so the evidence is inspectable by the human afterward rather than only claimed in prose.

Note the asymmetry with Cloudflare Codex's gate: that one is deterministic by construction — a build or test command either passes or it does not. A screenshot has no such built-in oracle. The verifier still has to decide what the pixels mean, which is exactly why who or what judges the evidence matters more here than in a code-only gate.

Where it is shipping

Kiro — verified: wires Playwright/browser MCP into its spec workflow for cross-breakpoint UI checks (Kiro blog).

Cursor — not one of the four named frameworks, but the strongest shipped evidence found. Verified: cloud agents run apps in VMs, click through UI, and attach video, screenshots and logs to PRs. Reportedly 30–40% of Cursor-ecosystem PRs merge without human review off that evidence — per a secondhand characterization (Arize AI), not a primary Cursor statement.

LangGraph, OpenAI Agents SDK, Microsoft Agent Framework — unverified. No evidence found of a built-in, wired implement→verify computer-use loop specifically for coding tasks in any of the three.

Where the confidence stops
The score rests on secondhand practitioner writeups — Vadim's blog, DevAssure, Arize AI — rather than the user's own measurement. No experiment has been run, and the hold on running experiments stays in effect, so this is researched and not measured. One provenance gap is carried forward rather than smoothed out: the TLDR AI source was traced and confirmed real — “The Computer Use Verification Skill That Every Agent Needs,” Aug 5 2026 edition — but its own primary author and URL could not be recovered, so provenance beyond the newsletter itself is unverified. The natural experiment, once the hold lifts, is self-graded versus code-graded verification on the same UI-change task, checking how often the two disagree — which the Verifiability axis is built to measure directly.
