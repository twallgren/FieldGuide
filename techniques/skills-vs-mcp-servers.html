Skills vs MCP Servers

Replacing always-loaded MCP servers with skills and plain scripts genuinely undercuts the token tax, and none of the four recurring axes gets worse to pay for it. It still costs a medium one-time build, and it is not a blanket replacement — MCP keeps the stateful and auth-brokered work.

What it does
Nothing recurring gets worse
The vector is +1 / 0 / +1 / 0. None of the four recurring deltas is negative, so nothing gets worse per turn once it is built, and there is no regime under which it is the wrong call. Two caveats survive the reclass, and both are scope rather than trade. It is not a blanket replacement: MCP remains the right choice for stateful and auth-brokered integrations, which is what the hybrid rule this note converged on already says. And the attention-delta: 0 is a cancellation of two real opposing costs, not an absence of cost — the upkeep is there, it just nets out.
What it costs to set up
effort: medium
Real, and deliberately kept out of the class. The one-time cost is authoring the SKILL.md files and writing the scripts that replace the tool calls, per integration migrated — spent up front, before any delta above starts paying. It amortizes and the deltas do not, which is why the rubric puts it on a different scale and says effort never determines the class. Note what is not here: keeping a skill current as the tool beneath it drifts is recurring upkeep, so it is priced into attention-delta, not into this panel.

Why each delta reads the way it does

cost-delta
+1
Not +2, deliberately

Skills genuinely undercut naive always-loaded MCP on token spend: 30-50 tokens per skill at rest versus tens of thousands for a handful of MCP servers with many tools. The numbers behind that — a five-server MCP setup can cost 50k+ tokens upfront, and the GitHub MCP server alone (43 tools, every schema loaded regardless of use) has been measured at ~62,000 tokens of overhead per 20-turn session before it does anything. Fifty skills is ~2,500 tokens.

Not +2: Claude Code's own deferred tool loading has closed a real chunk of this gap for MCP specifically, and a script still costs tokens to write and maintain (captured separately in effort) and to invoke when it runs. The delta is real but smaller than it would have looked before deferred loading existed.

That mechanism is ToolSearch: MCP tools default to name-only in context, with full schemas fetched on demand. The deep-dive session behind this note was a live example — dozens of MCP tools (Gmail, Google Drive, scheduled-tasks) sat as bare names in a <system-reminder> for the whole session, and only the two actually used had their schemas pulled in. So the original "MCP tools sit in context whether used or not" framing is now harness-dependent, not structural to MCP itself: true of Claude Code before deferred loading, and still true of clients that ship no equivalent — which is exactly the baseline above.

quality-delta
0
An uncertainty inside the zero

No source found evidence this changes task accuracy either direction. There is a real but uncertain trade inside it: an MCP tool's typed schema constrains what the model can even attempt to call — the Intervention Levers grid classifies Tools-lever constraint as "free, hard compliance" — while a skill's instructions are read and followed probabilistically, more like a rules file.

For simple stateless commands a deterministic script recovers that reliability; for anything more complex, swapping a typed tool for prose instructions could be a quiet quality cost that hasn't surfaced in any source reviewed here.

speed-delta
+1
Consistent across sources

Smaller resident context per turn means less to process before the model can act, consistent across every source discussing MCP overhead — "slower response times" is cited directly for large tool schemas.

attention-delta
0
Was +1 until 29 Aug

Two effects that cancel. Skills save the connection and auth babysitting an occasionally-used MCP server demands — fewer live moving parts per task. That much is the whole of what the earlier +1 saw.

But a skill is itself a part that must be kept alive by hand. An MCP server's schemas track its tools because whoever ships the server updates them; a SKILL.md keeps describing the old interface until a human notices, unless it is distributed through a channel with update support — a plugin or marketplace, rather than a hand-copied file. That maintenance moves from the vendor to me, it recurs, and attention-delta is the recurring axis, so it belongs here rather than in effort. A stale skill is also worse than none: confidently wrong about an interface the agent will then try to use. Net neutral.

dial
false
Design-time, not runtime

The hybrid rule is a design-time choice per integration — pick the right lever when building it — not a runtime knob a single task can flip the way model routing or reasoning-effort can.

Why this stopped being a trade
This page previously carried Class: trade, on the reasoning that the technique "spends build effort to buy cost and speed." That reasoning named exactly one spent axis — build effort — and build effort is effort, a one-time adoption cost, not one of the four recurring deltas the class is derived from. The rubric is explicit that effort never determines the class: a technique whose only cost is that it takes a weekend to set up is a no-regret that costs a weekend, and if setup counted, nearly everything with a setup step would be a trade and the distinction would stop carrying information. So the class was corrected on 29 Aug 2026, and the adoption cost was put on the page in its own right rather than laundered into the label — that is the second panel above, sitting beside the deltas rather than inside them. Read the class together with confidence: researched: the vector it is derived from rests on someone else's measurements, not a trial run here.
