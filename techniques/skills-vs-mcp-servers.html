Skills vs MCP Servers

Replacing always-loaded MCP servers with skills and plain scripts genuinely undercuts the token tax — but it is not a blanket replacement, and the harness has already closed part of the gap that motivated it.

Reach for it when
You are cost-bound or latency-bound
Fewer resident tokens per turn is a direct win under both regimes. This is where the note says the trade is best evaluated.
It needs a case-by-case call when
You are quality-bound
The typed-schema-vs-prose-instructions gap means the swap needs a case-by-case call rather than a default "skills win." And regardless of regime, this is not a blanket replacement: MCP remains the right choice for stateful and auth-brokered integrations.

Why each delta reads the way it does

cost-delta
+1
Not +2, deliberately

Skills genuinely undercut naive always-loaded MCP on token spend: 30-50 tokens per skill at rest versus tens of thousands for a handful of MCP servers with many tools. The numbers behind that — a five-server MCP setup can cost 50k+ tokens upfront, and the GitHub MCP server alone (43 tools, every schema loaded regardless of use) has been measured at ~62,000 tokens of overhead per 20-turn session before it does anything. Fifty skills is ~2,500 tokens.

Not +2: Claude Code's own deferred tool loading has closed a real chunk of this gap for MCP specifically, and a script still costs tokens to write and maintain (captured separately in effort) and to invoke when it runs. The delta is real but smaller than it would have looked before deferred loading existed.

quality-delta
0
A trade hides inside the zero

No source found evidence this changes task accuracy either direction. There is a real but uncertain trade inside it: an MCP tool's typed schema constrains what the model can even attempt to call — the Intervention Levers grid classifies Tools-lever constraint as "free, hard compliance" — while a skill's instructions are read and followed probabilistically, more like a rules file.

For simple stateless commands a deterministic script recovers that reliability; for anything more complex, swapping a typed tool for prose instructions could be a quiet quality cost that hasn't surfaced in any source reviewed here.

speed-delta
+1
Consistent across sources

Smaller resident context per turn means less to process before the model can act, consistent across every source discussing MCP overhead — "slower response times" is cited directly for large tool schemas.

attention-delta
+1
Once built

Once built, a skill+script is lower-friction per task than babysitting an MCP server connection and auth for something used occasionally — fewer moving parts to keep alive. This is separate from the one-time authoring cost, which is captured in effort: medium rather than here.

dial
false
Design-time, not runtime

The hybrid rule is a design-time choice per integration — pick the right lever when building it — not a runtime knob a single task can flip the way model routing or reasoning-effort can.

The class and the vector disagree
The delta vector here is +1 / 0 / +1 / +1 — nothing is negative. Read strictly by the rubric, that derives to no-regret: nothing gets worse. The note nonetheless states the class as trade, and this page follows the note. The two are mutually exclusive, both are derived from the same vector, and this page does not resolve which is right. The note does give its reasoning, verbatim: "Class: trade, not no-regret. It spends build effort to buy cost and speed at flat-to-uncertain quality, and — per the hybrid rule this note already converged on and the Perspectives log entry above corroborates — it's not a blanket replacement: MCP remains the right choice for stateful/auth-brokered integrations regardless of regime." The spent axis it names is build effort, which lives in effort: medium and not in any of the four deltas — so the cost the class is claiming is one the vector structurally cannot show. Whether that is enough to override a derivation the rubric says falls out of the vector is left open here rather than decided.
