Knowledge-Injection Hooks

A hook fires on every prompt, checks the knowledge base, and injects what matches — retrieval at the right moment instead of loading everything up front or hoping the agent thinks to look. The discovery problem gets solved structurally; every turn pays for it.

Reach for it when
You are attention-bound or quality-bound
Strong under attention-bound — it matches the stated current regime — and under quality-bound, where discovery correctness compounds into durability.
It is weak or negative when
You are cost-bound or latency-bound
The added per-turn overhead is a real tax under both — unless failed manual retrieval was previously causing expensive rework.

Why each delta reads the way it does

quality-delta
+1
Not +2, deliberately

Structural discovery genuinely beats hope-based discovery — closing the loop deterministically at the Loop lever is a real improvement over a rules-file plea. The baseline's failure mode is precise: knowledge only helped if the agent chose to consult the right skill file. A hook makes consultation automatic and structural.

It stops at +1 because the note's own precision matters more than recall caveat is a real risk — false-positive injections actively mislead — and there is no measured false-positive rate yet to say how often that bites.

cost-delta
−1
Scales with the matcher

Every hook firing spends tokens on the injected pointer text, and a non-trivial matcher — embeddings, a local model — adds compute and latency overhead on every single turn. This lands on exactly the Constraint/Information-at-Context row in the lever taxonomy: tokens, every turn, forever.

Kept to plain grep plus pointers rather than payloads, this is a small cost. It grows with matcher sophistication. That is also why the injection discipline matters: inject pointers, not payloads where possible — "relevant: skill X, note Y" costs a few tokens and lets the agent pull what it needs, while injecting full documents recreates the context-bloat problem this solves.

speed-delta
−1
Synchronous, before every prompt

It adds a synchronous step before every prompt is processed — Claude Code's own docs cap UserPromptSubmit at a 30s timeout — so per-turn wall-clock goes up even if it saves iteration cycles later by avoiding failed searches.

That timeout is also a failure-cost concern, not just a latency one. A hook that times out has its output — including additionalContext — silently discarded; the prompt still reaches Claude, just without the injection. An embedding or local-model matcher needs to stay comfortably under that budget or the hook fails silently rather than loudly.

attention-delta
+1
The axis it is built for

This is the axis the technique is built for. It removes a manual "go find the right skill" step from the user or the agent on every relevant turn, directly attacking the discovery problem the technique starts from.

dial
false
Standing configuration

No per-task knob is exposed by anything verified here — it is a standing repo/hook configuration, not something toggled per task. A verbosity or injection-depth control is imaginable but unconfirmed in practice.

The other way to solve this

Fine-tuning open-weight models is the bake-it-into-weights alternative to the same problem: getting tribal knowledge to a place the agent can use it. The two are direct alternatives, and they are scored against each other from opposite ends — that page takes this technique as its baseline, scoring itself against "the current context-injection approach (skill/steering files re-sent every session)."

Read together, the delta vectors mirror: the fine-tune buys back the recurring per-session cost this hook pattern pays every turn, and pays for it with knowledge that can no longer be diffed, reviewed, or selectively corrected — which is precisely what a pointer to a skill file preserves.

Your AGENTS.md Is Holding You Back

Argues context engineering has moved from adding information to minimizing it — an overly detailed AGENTS.md or CLAUDE.md degrades agent performance rather than helping, and the fix is regularly revising and testing context documents, soliciting feedback from the agent itself about what is unhelpful, and keeping a record of past errors to refine over time. Runs directly against this technique's default framing of injection as a retrieval and precision problem: the risk here is volume itself, even of things nominally relevant.

Why AI Coding Agents Need Context Graphs

Argues coding agents fail in real codebases because scattered team context — ownership, relationships between typed entities — isn't discoverable at prompt time, and the fix is publishing an externally queryable context graph with ownership metadata over MCP. Agentic Search

Mistral's Agentic Search replaces one-shot retrieval with a five-operation loop (search, open, navigate, read, grep) so the model can inspect long documents, follow references, and verify an answer instead of accepting the first retrieved chunks — a Loop/Tools-lever version of "get the right knowledge in" that this note tracks mainly at the Context lever (matchers/injection hooks). Vendor-run tests report FinanceBench correctness rising from 26.7% to 86% with the loop enabled, with a different harness adding another 10.5 points on the same model — a large, if vendor-authored, quantified case that how retrieval happens (single-shot vs. navigable loop) can matter as much as what gets retrieved.

Placement
The intervention sits across loop and context — the hook fires structurally in the turn loop, and what it changes is what is in the context window — with information and noise-reduction as mechanisms. That placement is not just locally plausible: this is a named, first-class abstraction in at least one other framework. Microsoft Agent Framework's AIContextProvider/ContextProvider is explicitly "a pluggable context-assembly step that injects additional context into an agent's prompt at runtime with its own token budget," which is this pattern almost verbatim. That convergence is evidence the Loop×Context placement is right.
