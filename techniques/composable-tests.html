Composable Tests

Kent Beck's argument that a suite should be built from small, orthogonal, non-redundant tests that compose. Not AI-specific — tracked here because suite speed and failure localization change the economics of an agent's feedback loop.

An ad-hoc test suite with overlapping, redundant assertions across similar-looking test cases — the common byproduct of tests written incrementally, case-by-case, including by an agent generating tests without seeing the suite as a whole.

What it does
Nothing gets worse
None of the four recurring deltas goes negative, so there is no regime under which this is the wrong call and no second panel naming one. Beck's own framing is explicitly "make the whole suite better," not a tradeoff between properties. The honest qualifier is the confidence rung rather than a hidden cost: this is a no-regret asserted on a guess, which is a weaker claim than a no-regret backed by measurement — the shape of the verdict is unconditional, the evidence under it is not.
What it costs to set up
effort: medium
The only cost is a one-time refactor — consolidating redundant assertions into fewer, more targeted tests — kept separate from the delta vector per program convention, because it amortizes and the deltas don't. There is no shipped tooling that enforces test composability; it is a codebase-authoring discipline, not a harness feature.

Why each delta reads the way it does

speed-delta
+2
One worked example, not a benchmark

Beck's own worked example — 4 computation variants × 5 reporting variants — goes from 20 brute-force tests to 10 composed ones for equivalent confidence, roughly halving suite wall-clock for that shape of problem.

That figure is illustrative, not a measured benchmark across real codebases, and no independent source in this research pass reproduced a comparable number. General CI-speed literature agrees that redundancy reduction and parallelization both cut suite time, but none of it validates Beck's specific ratio.

attention-delta
+1
Judgment, not measurement

Orthogonal tests localize failures to one cause; overlapping tests mean a break requires figuring out which of several similar-looking failures is the real signal. This is judgment, not measured — plausible but untested against the user's own suites.

cost-delta
+1
Modest and indirect

Faster, better-localized runs mean fewer agent turns spent re-running or diagnosing redundant failures. Modest and indirect — the saving arrives via the loop, not from any single call getting cheaper.

quality-delta
0
Economics, not coverage

This changes the suite's economics, not what the suite verifies. Assuming coverage is preserved during consolidation — Beck's own caveat, echoed by a commenter he cites who worries about losing intermediate-state assertions — artifact correctness shouldn't move in either direction.

dial
false
An investment, not a knob

This is a one-time suite-design investment, not a per-task knob. It is a design-time technique — how the suite is built — not a runtime constraint the harness enforces.

The rung that governs the rest

The direction of every delta is well-reasoned from first principles and cross-checked against general test-suite and CI literature. But no source — Beck's post, the Shopify entry logged below, or this pass's search — measured the specific claim that orthogonal composition speeds up an agent's feedback loop. That is this program's own inference from Beck's general testing-craft argument, not something anyone benchmarked in an agentic-coding context.

Shopify Engineering, via TLDR Dev
shopify.engineering
Mobile E2E testing (TLDR Dev, 2026-08-21)

Shopify raised its mobile E2E suite's stability to 98% not by restructuring test composition (this note's angle) but by replacing a footgun-prone Appium/WebdriverIO wrapper — arbitrary pauses, assertions on view-hierarchy nodes instead of what's visually rendered — with a strict builder-style API that forces an assertion on every step, escape hatches prefixed UNSAFE_, and computer-vision element-finding that matches what a user actually sees. Same Environment × Feedback cell, different mechanism: this note's fix is suite-design (fewer, better-composed tests); Shopify's is tooling-design (an API shape that makes flaky assertions hard to write in the first place).

Why this is tracked at all
Beck is making a general testing-craft argument, not an AI one. It is on the board because it is a concrete, sourced instance of the "test-suite speed & determinism as an agent lever" coverage-gap candidate — Environment × Feedback, a cell with zero primary-lever coverage in the lever taxonomy. It is also the one place on this site where an unconditional class marker sits on top of the weakest confidence rung, and the note itself does not reconcile those two things. Nothing here resolves it; it is flagged rather than smoothed over.
