How thin this vector actually is

Read the four cards above as a set rather than one at a time. Three of the four recurring axes are flat, and the fourth is a +1 asserted at the weakest confidence rung. That is not a recommendation — it is close to a null result with one unmeasured exception attached.

The claim that would have made this page worth acting on was the original framing: that dynamic languages suit simpler tasks and static languages match or beat them once a project gets complex. A direct read of the primary source walked that back. The author ran two evals — a zstd-decoder implementation and a Pandoc task-driven-development task — and the pattern did not agree between them: dynamic languages clustered better on zstd at medium effort, while on Pandoc "neither language type dominates the other" even at the highest (ultra) effort level tested. The author's own strongest conclusion is that most claims about a particular language being good for LLM use "seem to be wrong... but it's not clear what's right." No independent source was found that measures a complexity threshold at all.

So quality-delta is 0 not because language choice was shown not to matter, but because the evidence that it matters fell apart on inspection. Scoring a lift here would have been repeating an unconfirmed claim as fact.

What is left is the token-cost observation, and it should be sized honestly: a minor tiebreaker on a decision you are already making for other reasons, not a reason to pick a language.

Why each delta reads the way it does

cost-delta
+1
The only thing that moved

The one claim from this technique that survives independent cross-checking: dynamic languages run meaningfully cheaper per unit of code by token count. A separately-sourced estimate puts concise dynamic languages at roughly 1/2 to 1/3 the token cost of static languages like Rust, Go, and C++ for equivalent code.

Not +2 because this is a token-count estimate for equivalent code, not a measured end-to-end session-cost comparison, and it says nothing about whether fewer tokens actually translates to fewer accepted-outcome dollars once retries are counted. The rubric's "token cost is per-outcome in reality" caveat applies and was not tested here.

quality-delta
0
The corrected half of the note

The original candidate's central actionable claim — static languages match or exceed dynamic on complex projects — is not something the primary source itself asserts with confidence. Its own two evals (zstd, Pandoc) disagreed with each other, and the author's conclusion is that most language-performance claims "seem to be wrong" with no clear alternative. The article also explicitly cautions that patterns from smaller, simpler evals do not generalize to the larger case.

No independent source was found that measures a complexity threshold. Academic work on static analysis as an LLM feedback mechanism — type-checker-guided fix verification, static-analysis-driven prompting reducing defect rates over iterative passes — shows static analysis can improve LLM output quality as a feedback loop, but that is a different mechanism (post-hoc verification signal) from "static languages are better project-scale substrate."

A Type System Is a Search Oracle
A Type System Is a Search Oracle

Argues a type system functions as a “search oracle” for agent code generation — stronger checkers (Rust, and the limit case Lean) reject more incorrect programs at compile time, so an agent can sample-and-verify its way to a correct answer: “a verifier you can call cheaply and trust completely turns a mediocre generator into a good one, because brute force becomes admissible.” C++ is used as a control: statically typed but permissive (UB, implicit conversions), so compiling carries far less guarantee than Rust. This is a distinct mechanism from this note's own token-cost finding — Environment×Capability (how much the compiler can verify) rather than Environment×Noise-reduction (tokens per line) — worth weighing against this note's 14 Aug 2026 correction that dropped the capability angle from frontmatter for lack of primary-source support. This is a new, independently-argued case for that angle rather than a repeat of the original unsupported framing, and does not itself move any of the four scored deltas.

Where to look instead
The one place in the primary source where a static-leaning pattern showed up at all was at the ultra effort setting on the harder (Pandoc) task — which points at reasoning-effort level as a more evidenced lever for complex-task performance than a language choice made once and locked in. "Raise reasoning effort on hard tasks" is the better-supported move than "pick a static language for hard projects." This note is kept on the board as a genuine instance of the Environment lever with a mechanism the other Environment notes don't use — noise-reduction, fewer tokens per unit of code — and as a textbook case of a claim repeated confidently from a source that is itself far less confident than the summary suggested.
