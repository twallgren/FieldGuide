Deterministic Agent Workflows

When an agent figures out a multi-step task once, freeze the successful pattern into deterministic, versioned code — so later runs execute reliably without re-reasoning, and tokens go only to the genuinely novel parts.

The knob it hands you
Who holds the plan
Claude Code's own docs frame the distinction exactly as who holds the plan: with subagents, skills, and agent teams, Claude decides turn-by-turn; with a workflow, the script decides. That choice — invoke a workflow or ultracode at all versus staying conversational — is the knob, and workflowSizeGuideline (small / medium / large / unrestricted) is a literal second detent on it: advice to Claude on how many agents to plan for, not a hard cap, with the runtime caps still applying underneath.
What each way buys
Freeze it, or leave it conversational
Turn it toward the script when the work is cost-bound and the shape is stable: a narrow, well-tested frozen flow reused many times. Turn it back toward conversation for a one-off exploratory task — a single large workflow run can cost more than the equivalent conversation, because of fan-out breadth. Which flows to freeze is the judgment call: high-frequency, stable-shape tasks (report generation, data validation, ticket filing) freeze well; investigation and diagnosis may not.

Why each delta reads the way it does

dial
true
Not no-regret, despite four positives

All four deltas are positive, which would normally read as a no-regret. It isn't one, and dial is the only class marker that does not fall out of the delta vector — so the reasoning has to be stated rather than derived.

The decisive evidence is that Claude Code exposes this as a literal per-task knob — workflowSizeGuideline (small/medium/large/unrestricted) and the choice to invoke ultracode or a workflow at all versus staying conversational — and the right setting genuinely depends on regime: cost-bound work wants a narrow, well-tested frozen flow reused many times; a one-off exploratory task is better left conversational, since a single large workflow run can cost more than the equivalent conversation.

And it is not no-regret because the upfront authoring effort and the one-off-run cost are real regressions when the task shape isn't stable or won't repeat.

cost-delta
+1
Amortized, not immediate

Once a flow is frozen and reused, you stop paying reasoning tokens to re-derive the same control flow every run, and only the genuinely novel leaf work spends model tokens — the core mechanism this technique describes, and Claude Code's own workflow-vs-subagent comparison table confirms "the orchestration itself" is what becomes repeatable.

Not +2: this is specifically an amortized, repeat-use saving. Claude Code's own docs warn a single one-off Dynamic Workflow run can use "meaningfully more tokens than working through the same task in conversation" because of fan-out breadth — up to 1,000 subagents. The win is real only once the same script gets rerun, not on first authoring.

quality-delta
+1
Capped by rot

Determinism removes one source of run-to-run variance — the orchestration path itself no longer drifts — and Claude Code's docs note a frozen script can bake in a repeatable quality pattern, for example independent adversarial review before reporting, every run instead of that check happening only when the model happens to think of it.

Capped at +1, not +2, because a frozen flow can also silently go stale as the underlying system changes — frozen flows rot, and versioning and re-validation matter the same as for any code. That is a durability risk this delta does not cancel out.

speed-delta
+1
Off the conversation's critical path

Frozen orchestration runs outside the conversation — Claude Code's workflow runtime executes in the background and the session stays responsive — and can fan out up to 16 concurrent agents instead of one turn at a time. Genuinely faster wall-clock for tasks that decompose into parallel leaf work.

attention-delta
+1
Not higher, and the reason is upfront

Once authored, a frozen flow needs less supervision per run — you approve the plan once, then it either runs unattended or you check in via /workflows rather than steering every turn.

Not higher, because authoring and reviewing the script and watching token spend — Claude Code explicitly flags "Large workflow" runs — is real upfront and ongoing attention cost that a pure conversational run does not have.

effort
medium
One-time, and separate from the deltas

Writing, reviewing, and validating the frozen script — or the Swamp Club model/definition pair — is a one-time cost distinct from the per-run deltas above. Claude Code lowers it by writing the script for you, but a human still needs to review it before trusting it on a repeated, unattended task.

scottspence.com
via TLDR Dev
Agentic Engineering: A Practical Guide

Argues the deterministic checks this technique already favors — tests, linters, type-checkers as feedback during execution — aren't sufficient alone: the checks must be paired with independent review, never letting the agent grade its own work, since "the same mistaken assumption can survive planning, implementation and self-review if all three stages share the same context." A concrete failure mode for why frozen/deterministic flows still need an outside check rather than trusting the agent's own pass/fail signal.

Reading the Swamp

Alessandro Franceschi's read of Swamp Club is a deep, sourced endorsement of the freeze-the-pattern idea specifically — he frames Swamp's type/definition split as "the Puppet resource abstraction layer, reborn for agents" and its core value as moving continuity for a "brilliant amnesiac" agent out of the human's head and into versioned, git-tracked substrate rather than letting one-off scripts rot. His only hesitation was Extensions (agent-capability packages) feeling like an ecosystem/trust question, not a doubt about the freeze pattern itself.

Where the confidence has to move next
This is researched, not measured — desk research against official and vendor docs plus one third-party technical blog, with no trial run behind it. The named next step is to convert one repetitive flow into a saved Dynamic Workflow and measure tokens-per-outcome against the current conversational version over a handful of real runs. Until that happens, the +1 on cost is a reading of someone else's documentation, not a result produced here.
