Knowledge Compressor

A GitHub Next research prototype that compresses technical documentation for LLM consumption before it ever reaches an agent's context — a one-time preprocessing pass over static reference material, not a compaction of conversation history. Compressing once and reusing many times drops the recurring per-read token cost without spending quality or attention to get there.

What it does
Nothing recurring gets worse
The vector is +1 / 0 / +1 / 0. None of the four recurring deltas is negative, so nothing gets worse per read once a document is compressed, and there is no regime under which it is the wrong call. Two things that look like downsides are already priced into the numbers rather than sitting outside them: the ~$2 / ~2,000-reuse break-even is scored as a cap on the cost win, not as a separate cost, and the risk that a compressed doc drifts out of sync with its edited source is priced into attention-delta: 0 — neutral rather than negative, but explicitly not free. One scope caveat rather than a trade: this fits stable, frequently-reused reference docs, not a one-off document read twice.
What it costs to set up
effort: medium
Real, one-time, and deliberately kept out of the class. There is no shipped tool to point at — GitHub Next's post gives no release or license status — so the one-time cost is building the pipeline: the question-extraction call, the separate no-context answerability check that discards anything the model can answer from world knowledge alone, and the agentic compression loop with a token-counting tool and a "keep going until a test question fails" stop condition. Then roughly $2 of compression compute per document. It amortizes and the deltas do not, which is why the rubric puts it on a different scale and says effort never determines the class. Note what is not here: re-compressing a document after its source changes is recurring upkeep, so it is priced into attention-delta, not into this panel.

Why each delta reads the way it does

cost-delta
+1
Not +2, deliberately

Recurring per-read token cost drops by roughly the compression ratio once a document is compressed — 52% in the one published example, where GitHub Next's own case study cut a documentation article from 996 to 480 tokens while the surviving test questions still checked out. That is a real recurring saving on every subsequent inclusion.

Capped below +2 because the win is conditional. The compression run cost roughly $2, which at then-current pricing means the technique only pays for itself after about 2,000 reuses of the compressed version — so a document edited faster than it accumulates ~2,000 reads never actually recoups the compression cost. Per the rubric's rule that effort does not determine class, that risk is scored here on the recurring axis, as a cap on the win, rather than folded into effort.

The cost shape is the opposite of a per-turn injection technique: this is upfront compute traded for a permanently smaller artifact, closer in spirit to build-time work than runtime work.

quality-delta
0
Parity is the goal

The technique's own goal is parity, not improvement: preserve the same answerable facts in fewer tokens. Scored 0 rather than positive because that is the honest ceiling of "compress without losing usefulness."

Not negative, because the validation step is a real check rather than an assertion. Auto-generated questions function as unit tests for the facts a reader needs to retain, each one first validated as actually answerable from the original text; the compression loop then re-tests after every edit and is deliberately pushed until at least one question starts failing, so it does not stop short of the real reduction boundary. Using retained-knowledge Q&A as the gate is what lets the compressor claim "cut in half without substantially reducing usefulness" rather than just "cut in half" — summarization-that-loses-facts is an old, easy failure mode, and the test mechanism is the interesting part, not the compression itself.

With one hole that GitHub Next names itself: a test question can pass even when the model answers from its own world knowledge rather than the now-shorter document, especially for facts that were common knowledge before compression. That overstates safety on well-known topics and understates it on exactly the genuinely novel facts the technique should be judged on.

speed-delta
+1
Modest and recurring

Fewer tokens to process per turn is a modest, recurring wall-clock and throughput win, independent of the cost saving.

attention-delta
0
Neutral, not free

The compression run itself is a one-time batch job, not an ongoing burden. Scored 0 rather than positive because of a real recurring risk: a compressed document that drifts out of sync with its edited source has to be noticed and re-compressed — the same staleness failure mode already logged for skill files generally in Skills vs MCP Servers.

This note does not currently have that risk backed by any usage report, so it is scored as neutral rather than negative. It is not free.

dial
false
Preprocessing, not a runtime knob

The compression pass runs before the document ever lands in context — a manual or scheduled batch step over specific reference files, not a session-time setting a single task can turn up or down.

A no-regret resting on one source
The class is derived correctly: the vector is +1 / 0 / +1 / 0 and nothing recurring gets worse. But the rubric is equally explicit that class and confidence must be read together — a no-regret says adopt unconditionally, and that instruction is only as good as the numbers under it. Here, all four deltas rest on a single published source plus general-literature corroboration of the mechanism rather than the implementation: the prompt-compression literature (LLMLingua's up-to-20x compression at under 2% quality loss on QA benchmarks) supports that semantic-preserving compression at this ratio is achievable in principle, but nobody has independently reproduced GitHub Next's specific pipeline, its self-named validation hole, or its cost and break-even numbers. It was also evaluated on GitHub Next's own case study rather than an independent benchmark, and generalization across content types and languages is explicitly unresolved in the source post. Treat this as "should be no-regret, on the evidence available" rather than settled — the same reading the rubric works through for Composable Tests. Scoring was done by an unattended triage-and-dive pass on 31 Aug 2026; the deltas rest on published evidence and judgment, not on outcomes observed here directly, and should be confirmed or revised before being treated as settled.
